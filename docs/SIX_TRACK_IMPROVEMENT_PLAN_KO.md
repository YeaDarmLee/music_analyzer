## 1. 현재 문제와 기존 실험 결과 요약

### 1.1 현재 구조
1. KJ Mel-Band RoFormer가 원곡을 `vocals`와 `inst`로 분리한다.
2. 2트랙은 KJ의 `vocals`, `inst`를 그대로 제공한다.
3. 6트랙은 KJ의 `vocals`를 유지하고, KJ의 `inst`를 `core4`에 입력해 피아노·기타·베이스·드럼을 분리한다. `other = inst − (piano + guitar + bass + drums)`.
4. `core4`는 Mega53(53 stems)의 헤드 33(piano), 20(guitar), 4(bass), 15(drums)만 남긴 파생 체크포인트이고, 공식 Mega53 출력과 비트 단위로 같다.

### 1.2 사용자 청취 점수와 측정 결과
| stem | 청취 점수 | 측정으로 확인한 사실 |
|---|---:|---|
| 보컬 | 90+ | KJ 출력은 충분하다 |
| 피아노 | 약 70 | `basic_6`(개발용 비교 기준) 대비 −1.1 dB, 심벌 대역 −6 dB |
| 기타 | 약 70 | 약 −1.3 dB |
| 베이스 | 80~90 | 거의 같음 |
| 드럼 | 사실상 0 | 실제 6곡에서 원곡 대비 −5 dB → −17 ~ −32 dB. 비교 기준 드럼 에너지의 71~98%가 `other`로 이동 |

- 손실은 `core4` 단계에서 이미 생기고, 후처리가 더하는 손실은 0.6 dB 이하다.
- 합성 평가(드럼 −2.2 dB)는 실제곡 실패(−11 ~ −28 dB)를 보여주지 못했다. 평가 방식 자체를 바꿔야 한다.
- 기각된 실험: 추론 파라미터 조정(효과 작고 비용 2.3배), Mega53 보조 헤드(악화), Wiener 정제(크게 악화).
- **주의: 위 에너지 이동 수치는 정답 stem이 없는 상태에서 `basic_6` 드럼을 비교 기준으로 쓴 값이다.** 정확한 누출률이나 정답 기반 품질 지표가 아니라 **참고 지표**다.
- 시험한 6곡은 모두 큰 소리로 마스터링된 팝·록이라 실패 조건을 분리하지 못했다.

## 2. 최종 목표와 변경 불가능한 아키텍처 조건

### 2.1 최종 목표
상업용 셀프호스팅 음원 분리 서비스의 **실제 청취 품질**을 올린다. 보컬, 피아노, 기타, 베이스, 드럼, `other` 모든 stem에서 **주관적 품질 90점 이상**이 최종 목표다. 80점 등 중간 값은 단계 진행용 게이트이며 최종 합격과 혼동하지 않는다(9.2절에서 구분).

### 2.2 변경 불가능한 조건
1. **KJ는 첫 번째 분리 단계로 유지한다.**
2. **후속 악기 분리 모델의 실제 입력은 반드시 KJ의 `inst`다.** 원곡을 직접 넣는 경로는 "원인 진단 실험"으로만 쓰고 제품 경로로 채택하지 않는다.
3. `other = inst − (piano + guitar + bass + drums)` 합 보존을 유지한다.
4. 외부 유료 분리 API나 클라우드 분리 서비스는 쓰지 않는다. 자체 서버에서 실행 가능한 모델만 쓴다.
5. production에는 아래 3절 기준을 통과한 가중치만 쓴다. 출처 불명(UNKNOWN) 체크포인트는 쓰지 않는다.
6. 모델 다운로드나 학습, 벤치마크 실행은 **4절의 테스트 격리·정리 시스템이 갖춰진 뒤에만** 시작한다.
7. 단계마다 통과 기준과 중단 기준을 미리 정하고, 결과가 나쁘면 억지로 채택하지 않는다. 계획에 없는 새 실험 루프는 사용자 승인 없이 열지 않는다.

## 3. 상업 라이선스 검증 기준과 후보 모델 판정표

### 3.1 판정 기준 (사용자 지정)
- 저자나 공식 배포자가 가중치를 포함한 배포물 전체에 MIT를 포괄 적용했다면, 가중치마다 별도 LICENSE 문구가 없어도 **후보로 검토할 수 있다.**
- 저자가 특정 가중치에 대해 MIT 적용 제외, 연구 전용, 비상업용이라고 명시했다면 **무조건 제외**한다.
- 출처가 불명확한 UNKNOWN 체크포인트는 제외한다.
- 코드가 MIT라는 사실만으로 가중치까지 MIT라고 단정하지 않는다.
- **학습 데이터의 권리 문제는 체크포인트 라이선스와 구분해서 별도 칸에 기록한다.** 가중치 라이선스가 허용이어도 학습 데이터 위험이 있으면 그 위험을 "별도 위험"으로 표시하고, 승인 여부는 소유자가 그 위험을 보고 결정한다.

### 3.3 외부 보고서의 주장 중 이번에 확인하지 못했거나 우리 자료와 어긋나는 것
- "KJ가 GPL에서 MIT로 재라이선스됨(2026-04-22)": **[미확인].** 우리가 확인한 근거는 위 README 표기뿐이다. 0단계에서 날짜와 원문을 확인한다.
- "Open-Unmix-HQ(aufklarer 변형)은 모델 카드에서 MIT": **[미확인].** 이전 조사에서 원본 Open-Unmix `umxl`은 README에 CC BY-NC-SA 4.0(비상업)으로 적혀 있었고 `umx`/`umxhq`는 명시가 없었다. 변형의 출처·근거는 확인 전까지 제외한다.
- "SCNet은 공개 가중치가 없다": 첫 번째 보고서는 MSST가 SCNet 체크포인트를 MUSDB18-HQ 학습으로 제공한다고 썼다. **두 보고서가 서로 모순**이고 직접 확인하지 않았다. **[미확인].** 어느 쪽이든 MUSDB 학습이면 별도 데이터 위험으로 기록한다(3.4절).
- "Spleeter는 MUSDB 기준 약 9 dB SDR": **[미확인] 그리고 다른 근거와 어긋난다.** 첫 번째 보고서가 인용한 논문 수치는 Wiener 필터 기준 drums 6.71 dB, bass 5.51 dB, other 4.55 dB였다. 9 dB대는 HTDemucs 계열 수치다. 이 계획서에서는 SDR 숫자를 후보 선택에 쓰지 않고, 같은 곡에서 직접 비교한 결과만 쓴다.
- "멜밴드 개수·필터 특성을 바꿔 튜닝": 사전학습 가중치에서는 **추론 설정으로 바꿀 수 없는 항목**(구조가 학습에 고정됨)이라 계획에서 제외한다.
- "시간 반전·피치 이동 TTA": 시간 반전과 피치 이동은 입력 분포를 바꿔 오히려 품질이 떨어질 수 있다. 이 계획의 TTA는 **채널 좌우 교환과 위상 반전**을 기본으로 하고 나머지는 실험 항목으로만 둔다.
- 보고서의 "SDR 중앙값 ≥ 90점(%)"은 SDR(dB)과 주관 점수가 섞인 표현이다. 이 계획서는 SDR(dB)과 청취 점수(0~100)를 따로 정의한다(9.2절).

## 4. 테스트 환경 격리·용량 제한·완전 정리 설계 (필수 선행 조건)

**이 절의 시스템이 완료되고 검증되기 전에는 모델 다운로드, 벤치마크, 학습을 시작하지 않는다.** 과거에 임시 WAV, 분리 결과, 캐시, 중간 산출물이 여러 폴더에 쌓여 몇 GB씩 차지한 문제를 처음부터 막는 것이 목적이다.

### 4.1 테스트 전용 저장 공간
- 테스트 전용 루트 하나만 쓴다: 환경 변수 `MUSIC_TEST_ROOT`(기본값 `<프로젝트>/test-workspace`, git 무시). 루트에는 센티넬 파일 `.music-test-root`가 있어야 하고, 없으면 어떤 도구도 이 폴더를 쓰거나 지우지 않는다.
- 실행마다 고유한 `run_id`(시간+난수) 디렉터리를 만든다.
```
test-workspace/
  .music-test-root          센티넬
  index.json                실행 목록: run_id, 상태, 시작/종료 시각, 소유 PID, 사용 용량, 예상 용량
  runs/<run_id>/
    inputs/                 입력 복사본(짧은 구간)
    work/                   KJ inst, 중간 WAV 등 (실행 끝나면 삭제 대상)
    outputs/                모델별 stem 출력 (기본: 지표 계산 후 삭제)
    cache/                  이 실행에 한정된 캐시
    report/                 지표 JSON, 설정, 로그 (작은 파일, 보관 가능)
  reports/                  보관하기로 한 소형 리포트 (WAV 없음)
```
- 운영 서비스(업로드, 결과물, DB, 작업 큐)와는 **물리적으로도 논리적으로도 분리**한다. 서비스는 `data/separation/…`, 벤치마크는 `MUSIC_TEST_ROOT/…`만 쓴다. 벤치마크가 임시 파일을 시스템 temp나 프로젝트의 다른 폴더에 쓰지 않도록 `TMPDIR`/`TEMP`와 라이브러리 캐시 경로(Torch, numba 등)를 실행 컨텍스트 안에서 `runs/<run_id>/cache`로 돌린다.
- 모든 벤치마크 코드는 직접 경로를 만들지 않고 **`RunContext`**(생성 함수) 하나를 통해서만 경로를 받는다. `RunContext` 밖에서 쓰는 파일은 정적 검사(테스트)로 막는다.

### 4.2 저장 공간 누적 방지
- 상한(설정 가능): 실행 1건당(기본 5 GB), 테스트 루트 전체(기본 30 GB), 디스크 여유 최소치(기본 20 GB 이상 남기기).
- 실행 시작 전에 **예상 사용량**을 계산한다(곡 수 × 구간 길이 × 44.1 kHz × 2ch × 4B × stem 수 × 모델 수). 예상치가 상한을 넘으면 시작하지 않는다.
- 실행 중 `RunContext`가 쓰기 전에 현재 사용량을 확인하고, 상한에 닿으면 **무제한 저장하지 않고 중단**한다(중간 WAV 정리 후에도 초과하면 실패 처리).
- 1차 테스트는 **30~40초 구간**으로 하고, 전체 곡 테스트는 필요한 경우에만 한다.
- 지표는 계산 직후 `report/`에 기록하고, 대용량 중간 WAV(`work/`, `outputs/`)는 기본값으로 **지표 계산 후 삭제**한다. 오디오를 남겨야 하면 `KEEP_TEST_OUTPUT=1`을 명시하고, 그때도 실행당 상한과 보관 기간을 따른다.
- 청취 평가용 파일은 별도 하위 폴더(`runs/<run_id>/listening/`)에 만들고, 평가가 끝나면 삭제한다.
- 보관 기간(기본 7일)이 지난 실행은 다음 실행 시작 시 자동으로 정리한다(`report/`는 `reports/`로 옮긴 것만 유지).

### 4.3 테스트 종료 후 완전 삭제
도구: `scripts/testws.py` (하나의 CLI)
| 명령 | 동작 |
|---|---|
| `usage` | 테스트 루트 총 용량, 실행별 용량, 정리 가능한 용량, 한도 대비 사용률 |
| `list` | 실행 목록(상태: 완료/실패/중단/진행 중/고아) |
| `new --est-gb N` | 예상 용량 점검 후 `run_id` 예약 |
| `clean --run-id X --dry-run` | 지울 파일과 용량을 보여 주고 아무것도 지우지 않음 |
| `clean --run-id X --yes` | 해당 실행만 삭제 |
| `clean --all --dry-run` / `--yes` | 전체 테스트 산출물 정리. 실제 삭제는 확인 문구(`DELETE ALL`) 입력 필요 |
| `clean --older-than 7d --yes` | 보관 기간 지난 실행 정리 |
| `orphans` | 종료 기록 없이 끝난 실행과 PID가 사라진 실행 목록 |

- 삭제 전 항상 **무엇이 얼마나 지워지는지** 출력한다. `--dry-run`이 기본이고, 실제 삭제에는 `--yes`(또는 전체 삭제의 확인 문구)가 필요하다.
- 소형 평가 리포트와 실험 설정(`report/`, `reports/`)은 따로 보관할 수 있다. WAV, 캐시, 중간 stem은 항상 삭제 가능해야 한다.

### 4.4 안전 장치 (삭제 도구가 잘못된 곳을 지우지 않도록)
- 모든 경로를 실제 경로(`realpath`)로 풀어 `MUSIC_TEST_ROOT/runs/` **안쪽**인지 검증한다. 안쪽이 아니면 거부한다.
- 센티넬 파일이 없거나, 루트가 프로젝트 루트·홈·드라이브 루트이거나, 심볼릭 링크·정션을 포함하면 삭제를 거부한다(링크는 따라가지 않는다).
- 보호 목록(어떤 옵션으로도 삭제 불가): `data/separation/{web,jobs,inputs,models,tools}`, `song/`, 원본 학습 데이터 폴더(설정), 모델 가중치, `separation/tests/fixtures/`, `docs/`, 사용자가 "보관"으로 표시한 항목.
- 서비스 서버가 실행 중이면 서비스 data root에 대한 어떤 정리도 하지 않는다(테스트 루트만 대상).

### 4.5 테스트 데이터 관리 자동화
- 실행 시작 전: 예상 디스크 사용량과 여유 공간 점검.
- 실행 종료 시: 잔여 임시 파일 점검(`work/`가 비었는지, 정해진 파일 목록 밖의 파일이 없는지).
- 실패하거나 강제 중단된 실행: `index.json`에 상태와 PID, 하트비트가 있어 고아로 추적하고 `orphans`로 확인·정리한다.
- 현재 사용량과 정리 가능 용량은 `usage`로 언제든 확인한다.

### 4.6 삭제 기능 자체의 안전성 테스트 (구현 시 함께 만들 자동 테스트)
1. 테스트 폴더만 삭제되고, 루트 밖 파일은 그대로인지.
2. 잘못된 경로, 상대 경로 탈출(`..`), 운영 경로, 프로젝트 루트를 입력하면 거부하는지.
3. 심볼릭 링크와 정션(루트 안에서 밖을 가리키는 것 포함)을 따라가지 않는지.
4. 삭제 후 `usage`가 0으로 돌아오는지, 센티넬과 `reports/`는 남는지.
5. 보호 대상(원본 데이터, 모델 가중치, 보관 표시 항목)이 어떤 옵션에서도 남는지.
6. `--dry-run`이 아무것도 바꾸지 않는지, `--yes` 없이는 삭제되지 않는지.
7. 상한 초과 시 실행이 중단되는지, 중단된 실행이 고아로 나타나는지.
8. 기존 `conftest.py`의 "서비스 data root 불변" 검사를 유지하고, 벤치마크 코드가 `RunContext` 밖으로 쓰지 않는지.

## 5. KJ 모델 개선 계획 (독립 작업 트랙)

KJ의 보컬 점수가 높다는 이유로 이 트랙을 생략하지 않는다. KJ의 `inst`에서 악기 성분이 손실되면 이후 어떤 악기 분리 모델도 복구하기 어렵다. 단, **보컬 품질을 크게 떨어뜨리면서 악기 보존만 높이는 방식은 허용하지 않는다.**

### 5.1 검토 항목
| 번호 | 항목 | 설명 | 비고 |
|---|---|---|---|
| K1 | 현재 KJ 기준선 측정 | 보컬 청취, `inst` 안의 악기 보존, `vocals`로의 악기 누출, `inst`의 보컬 잔류, 처리 시간·VRAM | 모든 비교의 기준 |
| K2 | 입력 경로 진단 | `core4`에 원곡 직접 입력, 입력 음량 −6/−12 dB | **진단 전용.** 제품 경로는 항상 KJ `inst` 입력 |
| K3 | 청크 길이·오버랩 | 청크 경계 아티팩트와 악기 보존 | KJ에 대해 측정한 적 없음 |
| K4 | TTA | 채널 좌우 교환, 위상 반전 평균 | 시간·VRAM 비용 측정 |
| K5 | 반주 정리 | KJ가 남긴 보컬 꼬리 제거(합 보존 유지) | 보컬 쪽 손실 여부 확인 필수 |
| K6 | 대체 KJ 계열 체크포인트·앙상블 | 3.4절 기준을 통과한 체크포인트만. 현재 후보는 Mega53 파생 `vocal2`(같은 데이터 위험). 다른 후보는 **[미확인]**(탐색 필요) | 새 체크포인트는 6절의 라이선스 절차를 먼저 통과 |

### 5.2 평가 방식
- **보컬 방어선**: 개선 전후 보컬 청취 점수가 떨어지지 않아야 하고(허용 하락폭은 사용자와 정함, 기본 0), 보컬 누출·잔향·찢김 체크 항목이 악화되지 않아야 한다.
- **`inst` 보존**: 같은 곡에서 개선 전후 `inst`를 `core4`(또는 후보 모델)에 연결한 **end-to-end 결과**로 비교한다. KJ 단독 지표만으로 판단하지 않는다.
- **2트랙과 6트랙을 각각 평가**한다. 2트랙은 `vocals`/`inst` 청취 점수, 6트랙은 6개 stem 점수의 변화를 본다.
- 정답이 없는 곡의 에너지 비교는 참고 지표로만 쓴다.

### 5.3 통과·중단
- 통과: 보컬 방어선을 지키면서 6트랙 드럼 또는 피아노·기타의 청취 점수가 의미 있게 오르거나(중간 게이트 기준은 9.2절), 2트랙 `inst`가 개선된다. 시간·VRAM이 허용 한도 안이다.
- 중단: 개선이 작거나(중간 게이트 미달) 비용이 한도를 넘으면 해당 항목을 기각한다. 성능이 좋아 보이는 항목을 **초기 처리 시간만으로 탈락시키지 않는다**(비용은 기록하고 사용자가 한도를 결정).

## 6. 악기별 사전학습 모델 탐색 및 비교 계획

### 6.1 탐색 절차
1. **후보 수집**: 상업 사용이 명시된 가중치를 찾는다(저자·공식 배포자의 배포물 전체 라이선스 선언 기준). 출처 문서, 정확한 체크포인트 이름·버전·해시, 가중치 라이선스 근거, 예외, 학습 데이터 권리를 3.4절 형식으로 기록한다.
2. **기준 미충족은 즉시 제외**: UNKNOWN, 비상업·연구 전용 명시, 저자가 MIT 제외를 명시한 체크포인트(예: Demucs).
3. **확인 불가(보류)는 확정하지 않는다**: 근거가 나오면 재판정한다.
4. 외부 유료 분리 API나 클라우드 서비스는 조사하지 않는다.
5. 새 후보는 악기별로 **어느 stem을 대체할 수 있는지** 표시한다(예: Spleeter 5stems는 drums·bass·piano를 제공하고 guitar는 없음).

### 6.2 현재 알려진 후보와 한계
- 드럼·베이스·피아노: Spleeter가 유일한 외부 후보이며 **현재 보류**(릴리스 자산 라이선스 근거 필요).
- 기타: 현재 상업 근거가 확인된 외부 후보 없음.
- 피아노·기타 모두 외부에 마땅한 후보가 없으면 8절(추가 학습)로 간다.
- Mega53의 다른 헤드/구성은 이미 시험했고(보조 헤드 악화), 같은 가중치를 다른 입력에 넣는 시험은 5절 K2에서 한다.

### 6.3 환경 호환성 (후보 확정 후)
- 후보가 다른 프레임워크(예: TensorFlow)를 요구하면 **별도 가상환경, 별도 프로세스 어댑터**로 격리한다. 본체 환경과 의존성 충돌을 만들지 않는다. 설치는 4절이 갖춰진 뒤 한다.
- 입력은 항상 KJ `inst`이며 sample rate 변환이 필요하면 어댑터가 처리하고 합 보존 검사를 통과해야 한다.

## 7. KJ와 악기별 모델을 통합한 end-to-end 평가

### 7.1 비교 구성
1. **기준선**: KJ(현재) + `core4`.
2. **KJ 개선 전후**: KJ(현재) vs KJ(개선) 각각에 같은 후속 모델을 연결.
3. **악기별 후보 비교**: 같은 KJ `inst`를 입력으로 후보 모델 대 `core4`.
4. **악기별 최적 조합**: 예) 드럼 = 후보 A, 베이스 = `core4`, 피아노 = 후보 B … 의 최종 6트랙.
5. 각 구성을 2트랙·6트랙 모두에서 비교.

### 7.2 측정 항목
- **드럼 에너지 보존**(참고 지표): KJ `inst` 대비 드럼 stem 에너지, `other`에 남은 에너지. 정답이 있는 세트(Set A)에서는 Drum Recovery Ratio와 Drum-in-Other Leakage를 정답 기반으로 계산한다. 정답이 없는 곡의 값은 "참고용 에너지 비교"이며 누출률이라고 부르지 않는다.
- **`other` 점검**: `other` 청취 시 실제 악기(드럼, 피아노 등)가 과도하게 남아 있는지 체크 항목으로 평가한다.
- **보컬 방어선**: 보컬 점수와 체크 항목이 기준선 대비 악화되지 않았는지.
- **청취 품질**: stem별 0~100 블라인드 점수와 체크 항목(킥·스네어 손실, 심벌 깨짐, 드럼 볼륨 펌핑, 다른 stem 혼입, 서스테인 잘림).
- **합 보존·무결성**: 합 오차, NaN/Inf, 클리핑, stem 간 중복(overlap matrix).
- **자원**: 곡당 처리 시간, 최대 VRAM, 디스크 사용량(4절 도구로 기록).

### 7.3 평가 세트
- **Set A (정답 stem 있음)**: 합법적으로 확보한 독립 stem. 마스터링 변형(압축, 리미팅, 클리핑, EQ, 리버브, 스테레오 확장, 코덱, 라우드니스)을 입혀 합성 평가가 실제곡 실패를 못 잡던 문제를 줄인다. SDR/SI-SDR/SIR/SAR와 위 정답 기반 지표를 계산한다.
- **Set B (실제 상용곡, 정답 없음)**: 사용자가 청취해 점수를 낸다. 곡은 장르가 다양해야 한다(팝/K-pop/J-pop, 록/메탈, 발라드/R&B, 어쿠스틱/재즈, EDM, 극단 사례). 6곡 단계는 기존 6곡을 쓰고 24곡 단계에서 확장한다.
- **두 세트를 섞지 않는다.** 학습에 쓴 곡은 어떤 평가에도 쓰지 않는다.
- 블라인드 운영은 기존 `make-listening-package.py` 방식을 재사용한다(이름·순서 숨김, 음량 맞춤, 정답표는 평가 후에 열기). 청취는 사용자가 하고, 저는 신호 분석과 집계만 한다.

### 7.4 RTX 3060 12GB에 대한 원칙
- VRAM·시간은 후보별로 **측정해서 기록**한다. 품질 개선 가능성이 높은 모델을 초기 처리 시간만으로 탈락시키지 않는다. 처리 시간 한도는 사용자가 정하고, 한도를 넘으면 "비용 문제"로 따로 표시해 논의한다.

## 8. 필요할 경우에만 진행할 추가 학습 계획

**착수 조건**: 6절의 사전학습 후보를 충분히 비교한 뒤에도 특정 악기가 최종 목표(90점)에 못 미칠 때, 그리고 사용자가 별도 승인했을 때만 시작한다. 시작 전에 이 절을 세부 계획서로 확장한다.

### 8.1 원칙
- **검증된 사전학습 모델의 파인튜닝을 우선**한다. 처음부터 학습하는 것보다 데이터와 시간이 적게 든다.
- 파인튜닝 출발점은 3.4절에서 **라이선스 근거가 충족된 가중치만** 쓴다. 현재 그런 가중치는 Mega53 파생(`core4` 등, 학습 데이터 위험 기록 포함)이다. 비상업·연구 전용으로 명시된 가중치(예: Demucs)와 UNKNOWN 가중치는 출발점으로도 쓰지 않는다.
- **학습 입력은 실제 서비스와 같은 구조**여야 한다: 정답 stem들을 합쳐 만든 믹스를 **KJ에 통과시킨 `inst`** 를 입력으로 하고, 목표는 해당 악기의 정답 stem이다. KJ를 개선하면(5절) 학습 입력도 그 버전으로 다시 만들어야 한다.
- 정답 stem이 있는 **평가 세트와 실제 상용곡 청취 평가 세트를 분리**하고, **학습에 쓰지 않은 곡으로 반드시 최종 평가**한다. 곡·아티스트 단위로 분할해 누출을 막는다.

### 8.2 데이터의 등급
| 등급 | 설명 | 사용 |
|---|---|---|
| 1. 실제 독립 원본 stem(권리 확인됨) | 직접 녹음, 위탁 제작, 학습 허가가 확인된 데이터 | 학습·평가 정답으로 사용 가능 |
| 2. 합성 stem(상업 허용 음원으로 렌더) | 상업 사용이 허용된 SoundFont·악기·MIDI로 직접 렌더 | 학습 보조. 가상악기 라이브러리의 학습 사용 권리는 개별 확인 필요 |
| 3. AI가 분리한 pseudo-stem | 분리 모델 출력으로 만든 가짜 정답 | **정답 데이터가 아니다.** 평가 세트에 쓰지 않는다. 쓰더라도 별도 등급으로 분리하고 효과를 따로 측정 |

- **완성된 WAV 파일만으로는 정확한 악기별 정답 데이터를 확보했다고 볼 수 없다.** 독립 stem이 있는 것만 정답으로 센다.
- 공개 데이터셋은 라이선스를 개별 확인한다. MUSDB18, MoisesDB는 학술·비상업 제약이 있어 학습과 평가 모두에 쓰지 않는다. Slakh2100 등 CC BY 계열은 사용 전에 렌더링에 쓰인 가상악기의 학습 사용 권리를 확인한다 **[미확인]**.

### 8.3 Suno AI 생성 WAV
- Suno의 유료 플랜에서 생성물의 상업적 사용이 가능하다는 사실은 **그 생성물을 AI 모델 학습에 쓰는 것을 허용한다는 뜻이 아니다.**
- 공식 약관과 별도 서면 허가를 확인하기 전에는 **Suno 생성물을 학습 데이터로 쓰지 않는다.** 약관 확인은 0단계 증거 정리에 포함하고, 결과는 [미확인]으로 시작한다.
- Suno가 제공하는 AI stem 분리 결과도 실제 독립 녹음 원본 stem과 같은 정답으로 취급하지 않는다(3등급 pseudo-stem).

### 8.4 규모를 정하는 단계 (아래 곡 수는 성능 보장이 아니라 검증용 가정이다)
| 단계 | 곡 수(가정) | 목적 | 다음 단계로 가는 조건 |
|---|---:|---|---|
| 파일럿 | 약 50곡 | 데이터 파이프라인 검증(KJ inst 입력 생성, 분할, 학습·평가 루프), 개선 신호 존재 확인, 시험 학습으로 시간·VRAM 측정 | 평가 세트에서 해당 악기 점수가 기준선보다 개선되는 신호가 있고, 데이터 권리 문제가 없음 |
| 타깃 개선 실험 | 약 150~300곡 | 부족한 악기에 대한 집중 개선 | 최종 평가(학습에 쓰지 않은 곡)에서 중간 게이트를 넘는다 |
| 확장 | 약 500~1,000곡 | 확장 여부는 앞 단계 결과로 결정 | 이전 단계의 개선 폭과 비용을 보고 사용자가 결정 |

- 위 곡 수는 "이만큼이면 된다"는 의미가 아니다. 단계별로 결과를 보고 줄이거나 늘린다.
- 학습 중 생기는 체크포인트, 로그, 캐시도 4절의 테스트 루트와 용량 상한을 따른다. 학습용 원본 데이터는 보호 목록에 올리고 삭제 대상에서 제외한다.

### 8.5 중단 기준
데이터 권리를 확인하지 못하거나, 파일럿에서 개선 신호가 없거나, 시험 학습으로 측정한 시간·VRAM이 감당할 수 없으면 해당 악기의 학습을 중단한다.

## 9. 단계별 실행 순서, 예상 일정, 성공·중단 기준

### 9.1 실행 순서
| 단계 | 내용 | 예상 일정(추정) | 선행 조건 |
|---|---|---|---|
| 0 | 계획 승인, 결정 사항 확정(11절), 라이선스 증거 정리·정정(3.5절), 저자 문의 문안 | 2~4일(저자 회신은 별도) | 없음 |
| 1 | **테스트 격리·정리 시스템 구현과 검증(4절)** | 2~4일 | 0단계 승인 |
| 2 | 평가 세트 준비(Set A 마스터링 변형 포함, Set B 곡 선정), 평가·분석 스크립트 정리 | 2~3일 | 1단계 완료 |
| 3 | 기준선 측정(KJ + `core4`)과 KJ 입력 진단(K1, K2) | 1~2일 | 2단계 |
| 4 | KJ 개선(K3~K6)과 end-to-end 비교 | 3~5일 | 3단계 |
| 5 | 악기별 후보 비교: 1곡 → 6곡 → 24곡 | 5~10일 | 3.4절 후보 확정, 4단계 결과 반영 |
| 6 | 통합 라우터 구성(악기별 최적 조합), 합 보존·중복 검사, 최종 6트랙 평가 | 3~5일 | 5단계 통과 |
| 7 | 서비스 반영(레지스트리·승인·`/licenses`·릴리스 설정 갱신, 테스트, E2E) | 2~4일 | 6단계 통과 |
| 8 | 추가 학습(필요 시, 8절) | 별도 계획서 | 사용자 승인 |
| 9 | 13트랙에 같은 교체 적용 | 별도 | 6트랙 확정 |

일정은 확정이 아니며, 단계마다 사용자 청취 시간이 들어간다.

### 9.2 성공·중단 기준
**중간 게이트(단계 진행용, 최종 합격이 아니다)**
- G1 — 1곡 단계: 어떤 후보가 해당 stem을 기준선보다 **중앙값 +20점 이상** 올리고 80점 이상이면 6곡으로 간다. 80점은 "계속 진행"의 기준이지 합격 기준이 아니다.
- G2 — 6곡 단계: 드럼 중앙값 85 이상, 6곡 중 4곡 이상 80 이상, 60 미만 곡 없음, 다른 stem(특히 베이스·보컬)이 기준선 대비 악화되지 않음이면 24곡으로 간다.

**최종 합격(목표 90점)**
- 24곡 Set B: **모든 stem(보컬, 피아노, 기타, 베이스, 드럼, `other` 점검)의 중앙값 90 이상**, 하위 10% 80 이상, 60 미만 곡 0개.
- Set A: 정답 기반 지표에서 기준선 대비 개선(드럼: Drum-in-Other Leakage 감소와 SI-SDR 향상, 피아노·기타: SI-SDR +2 dB 이상이고 SIR 악화 1 dB 이내 등. 정확한 임계값은 2단계에서 기준선을 측정한 뒤 사용자와 확정한다).
- 보컬 방어선 유지, 합 보존·무결성 통과.
- 최종 합격 전에는 어떤 중간 결과도 "목표 달성"이라고 표현하지 않는다.

**중단**
- G1을 못 넘기는 후보는 해당 단계에서 중단한다. 결과가 나쁘다고 DSP 보정으로 우회하지 않는다(별도 승인 시에만).
- 5절 항목은 개선이 중간 게이트에 못 미치거나 비용이 한도를 넘으면 기각한다.
- 4절 상한을 넘기면 실행을 중단하고 원인을 기록한다.
- 라이선스 근거가 확인되지 않은 모델은 평가 단계에 들어가지 않는다.

## 10. 위험 요소와 대응책
| 위험 | 영향 | 대응 |
|---|---|---|
| 상업 근거가 확인된 외부 후보가 거의 없음(현재 Spleeter 하나, 그것도 보류) | 사전학습 비교 폭이 좁아짐, 8절로 이동 | 6.1절 탐색을 계속하고, 확인되지 않은 것은 확정하지 않는다 |
| Mega53 파생 가중치의 학습 데이터 위험(저자가 직접 밝힘) | 법적 청구 위험을 사용자가 감수 | 3.4절에 별도 기록, 소유자 결정 사항으로 유지, 근거 표현 정정 |
| 현재 KJ/Mega53에 기대는 한 드럼 한계는 그대로 | 품질 목표 미달 | 5·6절 비교 후 8절 파인튜닝 |
| 평가 정답 부족(실제곡은 정답 없음) | 객관 판단 어려움 | Set A(마스터링 변형 합성) + Set B 청취 병행, 에너지 비교는 참고 지표 표기 |
| 청취 평가가 사용자 시간에 의존 | 일정 지연 | 단계 축소(1→6→24곡), 중단 기준 적용 |
| 테스트 산출물 누적(과거 사례) | 디스크 고갈 | 4절 격리·상한·자동 정리를 선행 조건으로 |
| 삭제 도구 오작동 | 운영 데이터·모델 손상 | 경로 검증, 센티넬, 보호 목록, dry-run, 자동 테스트(4.6절) |
| 다른 프레임워크 의존성 충돌 | 통합 비용 | 별도 환경·프로세스 격리 |
| 독립 모델 조합 시 합이 두꺼워짐·중복 | 합 보존 위반 | overlap matrix, 합 오차 검사, 병합 거부 조건 |
| 외부 보고서 수치·주장의 오류 가능성 | 잘못된 결정 | 미확인 표시, 직접 비교 결과만 근거로 사용 |
| KJ 변경이 2트랙까지 영향 | 2트랙 품질 변화 | 5.2절에서 2트랙을 별도 평가 |
| 추가 학습 데이터 권리, Suno 약관 | 법적 위험 | 8.2·8.3절, 권리 미확인 시 사용 안 함 |

## 11. 각 단계의 완료 조건 및 검증 체크리스트

### 결정이 필요한 사항 (0단계 전 확정)
1. 비상업 가중치를 오프라인 "측정용 자"로만 쓰는 것을 허용할지(기본: 허용하지 않음).
2. 청취 시험 곡의 수와 장르(6곡 → 24곡의 구성).
3. 처리 시간·VRAM 한도(곡 길이당).
4. 보컬 방어선의 허용 하락폭(기본 0).
5. 추가 학습에 쓸 수 있는 데이터(직접 녹음 가능 여부 등)와 Suno 약관 확인 여부.
6. 저자·배포자 문의를 보낼지, 누가 보낼지.
